# 性能基准（官方 js-framework-benchmark）

这一页放的是 yoya-ui 在官方 [js-framework-benchmark](https://github.com/krausest/js-framework-benchmark)
（`keyed` 分类）上的实测数字：`yoya-ui-core` 实现对比官方原生基线 `vanillajs`，同时给出上一发布版本的
锚点列，便于看改动带来的位移。

数字不是手写的：表格块由 `benchmark/results.json` 生成，
`npm run report:bench:write` 刷新、`npm run verify:dist` 校验，手工改数字会直接失败。
复跑步骤见 [benchmark/README.md](../benchmark/README.md)。

## 怎么读

- **script / paint 拆解**：官方 runner 把每次操作拆成 JS 执行（script）与渲染（layout / paint / commit）。
  yoya-ui 的绘制桶已经与原生基线持平（9 项里差 0.2～3 ms，落在噪声内），剩余差距全部在 script 桶与内存。
- **create 类操作是主战场**：`01 / 07 / 08` 三项的 script 差距最大（1k 行 ~18 ms、10k 行 ~195 ms），
  对应节点对象构造、登记与首次写 DOM 的成本；`03 / 04 / 05 / 06` 这类增量操作已经接近原生。
- **清空路径已经追平**：`09_clear1k_x8` 从 58 ms 降到 22.5 ms（原生 15.5 ms），这是销毁路径改单趟 +
  批量摘除的结果。
- **`04` / `03` 反映的还有条目自身的状态模型**：yoya 条目用共享 `selectedId` 派生每行的选中类
  （`computed(() => selectedId.value === row.id)`），一次点击会唤醒全部行——与 Vue 条目的
  `:class` + `v-memo` 同形；React 条目把选中态按行传入并用 `memo` 比较；只有手写的原生基线只碰
  受影响的两行。看 `04` 这一格时要记得这一点；O(1) 的替代建模见 `docs/component-authoring.zh-CN.md` §6.2。
- **内存仍是最大量级差**：建 1000 行后 6.15 MB vs 原生 2.45 MB（2.51×），比 0.6.2 的 11.03 MB 降了
  44%；剩余部分主要是 DOM 对象与 V8 节点对象头。
- **体积是已知代价**：核心不可 tree-shake 的部分让单页体积是原生的 5～7 倍（62.7 KB / 17.1 KB brotli vs
  11.7 KB / 2.5 KB brotli），这是「一套 DSL + 组件库」与「手写 DOM 调用」的固有差别。
- **first paint 是单次采样**：官方 runner 只采一次，本机 5 次重复的实测区间约 303～410 ms（中位数
  306.8 ms），表里那一格不要当精确值看；它也因此不适合用来判断 KB 级体积变化。

## 跨口径不可比

本仓库还维护一套自建 harness（`.scratch/perf-1x/`，msedge headless，按 1000 行的 MB 增量取数），
用于改动前后做同机对照。**两套口径的绝对值不可互换**：官方 runner 用的是 Chrome for Testing 152 +
playwright、按操作计时；自建 harness 直接读 `performance.measureUserAgentSpecificMemory()` 的行增量。
同一份 0.6.2 代码在两套口径下的读数差可达 1.5～3 倍（例如建 1k 行的 script：官方 26.0 ms、自建 14.6 ms），
所以对比只能在口径内纵向进行。
